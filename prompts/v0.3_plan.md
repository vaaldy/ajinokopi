# v0.3 — release CI/CD

## Context

v0.1 and v0.2 shipped. Deployment still "build on laptop and hope". `status.md` has carried
*Deploy to GitHub Pages* in Todo since rev 3. Make releasing one act: **bump `version` in
`package.json`, push to main — rest is automatic.** Tag, build, deploy, GitHub Release.

App is a static Vite bundle. No backend, no env vars, no secrets to inject, so whole pipeline is
install → test → build → publish a folder. Repo `vaaldy/ajinokopi`, default branch `main`.
`vite.config.js` already sets `base: './'` for Pages subpaths.

**Deliberately simple.** No preview environments, no changelog tooling, no release-please. If this
plan needs a diagram, it failed.

## Decisions (confirmed with user)

- **Trigger = semver bump on main.** Push to `main` changing `version` in `package.json` creates
  and pushes matching `v<semver>` tag; that release runs. No hand-typed `git tag`.
- **Target = GitHub Pages**, built by Actions, not from a committed `dist/` (stays gitignored).
- **pnpm**, not npm — see prerequisite 2.

## Prerequisites (nothing works until these land)

1. **Commit v0.2 work.** `src/wheel.jsx` untracked. CI builds what is committed, so today it
   would deploy a different app than the laptop — and `pnpm test` imports `layoutPills`/`layoutWheel`,
   so it would not even build.
2. **One lockfile.** `pnpm-lock.yaml` (lockfileVersion 9, `node_modules/.pnpm` present) is real and
   untracked. `package-lock.json` is from Aug 11 and *is* tracked. Commit the pnpm lock,
   `git rm package-lock.json`. CI installs with `--frozen-lockfile`, which fails loudly rather than
   silently resolving a different tree — only helps if committed lock is the true one.
3. ~~**Add `version` field.**~~ **Done** — `package.json` carries `"version": "0.2.0"`, set when
   v0.2 closed. Below 1.0.0 because phone UAT has not happened. First automated release = first
   bump after this.
4. **Add `"packageManager": "pnpm@11.3.0"`** so `pnpm/action-setup` pins CI to the laptop's pnpm
   instead of drifting to latest.
5. **One-time repo setting:** Settings → Pages → Source = **GitHub Actions**. Not a file, cannot be
   scripted here. Without it the deploy job fails on an otherwise perfect run.

## The one real design constraint

**A tag pushed with default `GITHUB_TOKEN` does not trigger another workflow.** Deliberate GitHub
guard against recursive runs. So the obvious shape — "`tag.yml` pushes a tag, `release.yml` listens
on `push: tags`" — does nothing, and failure mode is a green tagging run then silence. Three ways out:

- **(a) PAT** — repo-scoped token in secrets. Works, but a credential to store, scope, rotate, for a
  public static site needing no other secret.
- **(b) Reusable workflow** — `release.yml` declares *both* `workflow_call` and
  `push: tags: ['v*.*.*']`. Tagger invokes it via `uses:` after pushing the tag. No credential, and a
  hand-pushed tag still works as escape hatch. **Chosen.**
- **(c) One monolithic workflow** — simplest to read, but a manually pushed tag then has no entry point.

## Files

```
.github/workflows/
  ci.yml        — push to main + PRs: install, test, build. Proves green. Deploys nothing.
  tag.yml       — push to main touching package.json: detect bump, test, tag, call release
  release.yml   — reusable + tag-triggered: build → deploy Pages → GitHub Release
```

### `ci.yml`
`on: push: branches: [main]` + `pull_request`. One job: checkout, `pnpm/action-setup`,
`actions/setup-node` with `cache: pnpm`, `pnpm install --frozen-lockfile`, `pnpm test`, `pnpm build`.
~20 lines. Everyday signal. Allowed to be boring.

### `tag.yml`
`on: push: branches: [main], paths: ['package.json']`.

- `actions/checkout` with **`fetch-depth: 2`** — default depth-1 checkout has no `HEAD~1` to diff
  against. Easiest thing to get wrong here.
- Read `version` at `HEAD` and from `git show HEAD~1:package.json`. Unchanged → exit 0 quietly
  (a push touching `package.json` for a dependency is not a release).
- Validate against `^[0-9]+\.[0-9]+\.[0-9]+(-[0-9A-Za-z.-]+)?$`. Junk → fail loudly.
- If `git rev-parse v$VERSION` resolves, tag exists → fail with "version already released, bump
  again" rather than clobbering.
- **Run `pnpm install --frozen-lockfile && pnpm test` before tagging.** Ordering matters: a tag is
  the permanent record of a release, so a red tree must never earn one. Test first, then tag.
- Create annotated tag (`git tag -a v$V -m "v$V"`) as `github-actions[bot]`, push it, then second job
  `uses: ./.github/workflows/release.yml` with `permissions` declared on the caller.

### `release.yml`
`on: workflow_call` **and** `on: push: tags: ['v*.*.*']`.

- `permissions: { contents: write, pages: write, id-token: write }`.
- `concurrency: { group: pages, cancel-in-progress: false }` — never let two deploys interleave.
- Job **build**: install, `pnpm test` (cheap, and tag-triggered path has not run it), `pnpm build`,
  `actions/upload-pages-artifact` with `path: dist`.
- Job **deploy**: `environment: github-pages`, `actions/deploy-pages`.
- Job **release**: create GitHub Release for the tag with auto-generated notes (`gh release create
  --generate-notes`, or `softprops/action-gh-release`). No artifact attached — the deploy *is* the artifact.

Pin Node 22 (Vite 7 needs ≥20.19/22.12; laptop on 26, so 22 is the conservative floor that still
builds). Pin every action to a major version tag.

## Implementation order

1. Prerequisites 1–4 (commit wheel.jsx, lockfile swap, `version`, `packageManager`) as one commit.
2. Prerequisite 5 in repo settings UI.
3. `ci.yml` alone. Push, confirm green. Validates install/test/build triple in CI before anything deploys.
4. `release.yml`. Test by hand: `git tag v0.2.0 && git push --tags` → Pages goes live. Proves deploy
   path in isolation, no tagging logic in the way.
5. `tag.yml`. Test with a real bump to `0.2.1`.
6. Docs: `prompts/v0.3.md`, move *Deploy to GitHub Pages* out of `status.md` Open.

## Acceptance criteria

- Bump `version` 0.2.0 → 0.2.1, push to main. Within ~2 min, touching nothing else: tag `v0.2.1`
  exists, Pages serves new build, Release `v0.2.1` listed.
- Push to main *not* changing `version` runs `ci.yml` and nothing else. No tag, no deploy.
- Red `pnpm test` → **no tag created at all**, not a tag whose deploy failed.
- Same version pushed twice fails with a clear message, not a duplicate-tag error or silent second deploy.
- `git tag v9.9.9 && git push --tags` by hand still deploys. Escape hatch survives.
- Phone at `https://vaaldy.github.io/ajinokopi/`: wheel renders, `flavors.yaml` loads. `App.jsx`
  fetches it as *relative* `'flavors.yaml'`, so this is the check that `base: './'` and the Pages
  subpath agree.

## Verification

- Locally, run CI's exact sequence before writing any YAML:
  `pnpm install --frozen-lockfile && pnpm test && pnpm build && pnpm preview`. If `--frozen-lockfile`
  fails, prerequisite 2 is not done.
- Confirm `dist/index.html` references `./assets/...`. Relative paths are what make Pages subpath
  hosting work; absolute `/assets/...` would 404 there and only there.
- Prototype the version-diff as a plain shell one-liner locally
  (`git show HEAD~1:package.json | node -p "JSON.parse(require('fs').readFileSync(0)).version"`)
  before it goes into YAML, so debugging happens in a terminal, not in the Actions log.
- Watch first real release live in the Actions tab. Not fire-and-forget.

## Skipped (add when needed)

- **npm publish** — private app, not a library.
- **Changelog tooling** (release-please, changesets, conventional commits) — GitHub auto-generated
  notes are enough until a second person reads them.
- **Per-PR preview deploys** — one contributor, one environment.
- **Staging environment** — nothing to stage against, no backend.
- **Signed tags / build provenance / SBOM** — no supply chain to speak of.
- **Lighthouse, visual regression, Playwright in CI** — UI still moving after v0.2 UAT. Add once
  gestures settle, and add to `ci.yml`, not the release path.
- **Rollback automation** — re-bumping to a fixed version is the rollback.
